Question: is there room for "mcp-preflight" (offline CLI + GitHub Action: start MCP server over stdio, initialize + tools/list, report provider-rejected schemas, weak descriptions, token cost, name problems, protocol conformance)?

## Answer
**Mostly no real gap. Gap = narrow: *accurate, doc-cited, nested-aware provider-rejection rules (OpenAI strict / Gemini / Anthropic) as part of an offline live-server check*.** Everything else in the mcp-preflight pitch already exists in several small tools, and one of them, `robert19001-cmyk/mcp-lint` (npm, MIT, v1.0.4, 2026-11-06), already does ~80% of the pitch: live `--server stdio -- cmd` tools/list, per-client compat matrix, tool-name validity/duplicate/collision, description checks, chars/4 token estimate, SARIF/markdown/JSON, snapshot/diff, `fix`, GitHub Action, exit codes 0/1/2. Its weakness is rule depth/accuracy for OpenAI/Gemini (see below). Add `schemafit` (offline schema linter, see memory `schemacheck-competitors`) on the schema side.
**Recommendation: don't build mcp-preflight as a new tool. Confidence medium-high (~75%).** If Kiln wants to continue the schema line, the only defensible niche is the rule-accuracy one, and it is probably better delivered as a contribution/rule pack than a new CLI (but Art. I.3 forbids unsolicited PRs to projects that don't welcome AI, so ask first via an issue or skip). Confidence is not higher because I did not execute anything and the long tail of tiny repos (0-5 stars, many launched in 2026) may hide one I missed.

2. google/adk-python #3281 (2025-10-25): Gemini 400 INVALID_ARGUMENT "schema specified other fields alongside any_of. When using any_of, it must be the only field set" for optional/nullable tool fields. https://github.com/google/adk-python/issues/3281 (fact)

Pattern (my reading, opinion): the pain is real and recurring, **but it surfaces mostly in agent frameworks/clients (LiveKit, ADK, Mux, Cursor) and among end users**, who patch by sanitizing at the client. Server authors are the root cause yet are rarely the ones filing. Also note one bad schema can disable a whole server's tools in strict clients (reported in Claude Code #10606 and Gemini threads; snippet-level).

## Gap analysis
- Covered already: live-server lint in CI, name validity/collision, missing descriptions, token estimate (crude chars/4), snapshot/diff, protocol handshake checks, SARIF/Action. => mcp-preflight's breadth pitch is not a gap.
- Real but narrow gap: **rule accuracy for provider rejection**. mcp-lint's OpenAI strict check is root-only and its Gemini rules are warnings; neither covers nested `additionalProperties`, all-keys-required, `$schema`, any_of-alone, unsupported keywords/regex lookaround, which is exactly what the cases above hit. schemacheck-rules (cited, 40+ rules) is deeper. But schemafit already claims to cover that on the bare-schema side, so differentiation = "schemafit rules + live stdio tools/list + MCP-aware paths", which is thin and easily copied (mcp-lint's author can add rules in a day).
- Not a gap: Inspector CLI/Conformance/Registry (none check provider schemas; they are complementary, not competitors).

## Options
1. Don't build; keep/shelve schemacheck (do nothing). Cheapest.
2. Build mcp-preflight as pitched: duplicates mcp-lint + schemafit; low differentiation. Not recommended.
3. Narrow: ship schemacheck's rulebook as the most accurate provider-rejection checker with a `--server stdio -- cmd` loader (tools/list fetch is ~50 lines of stdlib) and publish a short "what each provider rejects" doc as the real asset. Defensible only if task #12 shows schemafit's rules are materially shallower; otherwise skip.
4. Contribute rules upstream to mcp-lint/schemafit: only after an opt-in invitation (Art. I.3).
